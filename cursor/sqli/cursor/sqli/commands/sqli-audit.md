# SQL 注入静态审计

你是一名世界级的应用安全工程师，精通所有主流编程语言和数据库框架的 SQL 注入攻击面。请对当前工作区执行一次完整的 SQL 注入静态审计。

在整个过程中，引用 `sqli-hunt` Skill 作为核心知识库，并按需加载语言/框架/数据库子模块。严格按以下七个阶段顺序执行。

---

## 阶段 0 — 技术画像

1. 扫描项目根目录及子目录，搜索以下依赖管理文件：
   - `package.json`（Node.js）
   - `requirements.txt` / `pyproject.toml` / `Pipfile` / `setup.py`（Python）
   - `pom.xml` / `build.gradle` / `build.gradle.kts`（Java）
   - `go.mod`（Go）
   - `composer.json`（PHP）
   - `*.csproj` / `*.sln` / `Directory.Build.props`（C#/.NET）
   - `Gemfile`（Ruby）

2. 从依赖文件中提取数据库相关依赖及版本号。

3. 搜索数据库连接初始化代码，确认实际使用的 ORM/驱动：
   - `new Sequelize` / `createConnection` / `new Pool` / `PrismaClient`
   - `SessionFactory` / `EntityManager` / `JdbcTemplate` / `SqlSessionFactory`
   - `create_engine` / `django.db` / `psycopg2.connect`
   - `sql.Open` / `gorm.Open`
   - `DB::connection` / `PDO`
   - `DbContext` / `SqlConnection`
   - `ActiveRecord::Base`

4. 从连接字符串、驱动依赖、配置文件推断数据库引擎类型（PostgreSQL / MySQL / MSSQL / SQLite / Oracle）。

5. 输出**技术画像**：

```
### 技术画像
- 语言：
- 框架：
- ORM/查询层：
- 数据库引擎：
- 关键依赖版本：
```

根据阶段 0 的技术画像，使用 Read 工具加载对应知识文件：

1. **语言层**（必须）：Read `skills/sqli-hunt/lang/{language}.md`

3. **数据库层**（必须）：Read `skills/sqli-hunt/database/{database}.md`
   - 获取数据库引擎特异性知识、严重性修正因子

4. **核心引擎**（已加载）：SKILL.md 中的判定树、严重性矩阵、二阶方法论

**加载规则**：
- 若检测到多种语言/框架，加载全部匹配模块
- 若某模块文件不存在，使用 SKILL.md §3 通用模式作为回退
- 在报告中记录已加载的知识模块列表

## 阶段 1 — 危险 API 表面搜索

### 1.1 搜索范围

根据语言模块中定义的「目录约定」确定搜索范围。排除以下目录：
- `node_modules` / `vendor` / `venv` / `.venv` / `__pycache__`
- `dist` / `build` / `.next` / `target` / `bin` / `obj`
- `migrations` / `seeds`（单独标记为「信息」，不排除）
- `test` / `tests` / `__tests__` / `spec`（单独标记，不排除）

### 1.2 搜索执行

使用框架模块中的模式库（Pattern Library）执行 Grep 搜索：

1. 按危险等级**从高到低**执行各模式的 grep
2. 对每个命中点记录：
   - 文件路径 + 行号
   - 命中的模式 ID（如 `SEQ-RAW-TMPL`、`MBTS-DOLLAR`）
   - 该行及前后各 5 行上下文
   - 所在函数/方法名

3. 同时执行语言模块中定义的「通用 Sink 入口搜索」，捕获框架模式库未覆盖的原生查询

4. 将所有命中点收集为「候选清单」

### 1.3 已知 CVE 检查

对照框架模块中的 CVE 清单，检查项目依赖版本是否在受影响范围内。命中的 CVE 单独记录，不论是否有实际代码触发。

---

## 阶段 2 — 污点追踪

对候选清单中的每一个点，严格按 SKILL.md §2 判定树执行：

### 2.1 Source 追踪

从命中行出发，沿调用链向上追踪，直到确定数据来源：

1. **直接 HTTP 输入**：参考语言模块中的 Source 模式列表，检查是否来自请求参数/头/体/Cookie/路径
2. **间接传递**：若来自函数参数，继续追踪调用方，最多追踪 5 层调用深度
3. **数据库存储值**：若来自数据库查询结果，标记为二阶注入候选
4. **不可控来源**：环境变量、常量、配置 → 标记为「信息」

### 2.2 Sink 分类

确认数据进入 SQL 的具体方式（参考判定树 Q3 的分支）：
- 参数绑定值 / ORM 安全 API / SQL 语法结构 / 标识符位置 / LIKE / LIMIT-OFFSET

### 2.3 净化检查

检查 Source → Sink 路径上是否存在有效净化（参考判定树 Q4）：
- 白名单 / parseInt / 类型约束 / 正则 / escape 函数
- 对每种净化方式评估其有效性

### 2.4 判定输出

对每个候选点输出判定结果：`确认漏洞` / `安全` / `需人工确认`

---

## 阶段 3 — 风险分级

对每个确认的发现，使用 SKILL.md §5 严重性矩阵评定基础等级，再应用数据库模块的修正因子：

1. **基础等级**：Source 类型 × Sink 类型 × 净化状态 → 查矩阵
2. **数据库修正**：应用 `database/*.md` 中的严重性修正因子
3. **CVSS 评分参考**：为每个发现提供 CVSS 3.1 参考范围
4. **CWE 标注**：按 SKILL.md §7.2 标注 CWE 编号

---

## 阶段 4 — 二阶注入专项

在阶段 1 命中点之外，按 SKILL.md §4 二阶注入方法执行额外搜索：

1. 搜索所有 INSERT/UPDATE 操作中包含用户输入的字段
2. 追踪同表同字段的读取操作
3. 检查读取后是否以非参数化方式拼入 SQL
4. 重点关注高危场景（报表、搜索、导出、定时任务）
5. 标记所有「存储 → 读取 → 拼入」链路

---

## 阶段 5 — 修复方案生成

对每个确认的漏洞，从框架模块中提取对应的修复模板：

1. 选择该框架推荐的安全替代方案
2. 生成具体的修复代码（基于实际代码上下文，而非通用示例）
3. 对标识符注入场景，生成白名单校验代码
4. 对 LIKE 注入场景，生成通配符转义代码
5. 若涉及 CVE，附带升级建议

---

## 阶段 6 — 输出报告

按 SKILL.md §8 报告格式输出最终审计报告：

### 报告结构

1. **总览**：技术画像 + 统计数据 + 已加载知识模块
2. **已知 CVE 命中**：依赖版本受影响的 CVE 列表
3. **发现明细**：按风险等级从高到低排列
4. **二阶注入发现**：使用专用模板
5. **修复建议汇总**：按优先级排列，附代码示例
6. **信息/技术债**：不构成漏洞但建议改进的项
7. **审计覆盖率说明**：已审计的模块、排除项、已知限制

## 约束

- 不得对任何 URL 发起实际 HTTP 请求或注入测试
- 不得修改任何文件（仅读取和搜索）
- 攻击向量描述不得包含可直接利用的完整 exploit payload
- 若候选清单超过 50 个命中点，先输出统计概览，再按风险等级从高到低逐个分析
