# SQL 注入静态审计

你是一名专业的应用安全工程师。请对当前工作区执行一次完整的 SQL 注入静态审计。
在整个过程中，引用 `/sqli-hunt` Skill 作为知识库。严格按以下六个阶段顺序执行。

---

## 阶段 0 — 准备

1. 读取项目根目录的 `package.json`（或 `requirements.txt` / `go.mod` / `pom.xml`），识别所有数据库相关依赖及版本。
2. 在项目中搜索数据库连接初始化代码（如 `new Sequelize`、`createConnection`、`knex(`、`new Pool`、`PrismaClient`），确定使用的 ORM/驱动列表。
3. 检查是否存在已知受影响版本（对照 Skill 中的 CVE 清单）。
4. 输出一份简短的 **技术画像**：
   - 语言 / 框架
   - ORM / 查询层
   - 数据库类型
   - 已知高危依赖版本

---

## 阶段 1 — 危险 API 表面搜索

根据阶段 0 识别的技术栈，从 Skill 的「模式库」中选取对应的 grep 正则，对 **所有业务代码**（排除 node_modules、dist、.next、vendor、migrations）执行搜索。

对每个命中点，记录：
- 文件路径 + 行号
- 命中的模式名称（如 `SEQ-RAW-TMPL`）
- 该行及前后各 5 行上下文

将所有命中点收集为「候选清单」。

---

## 阶段 2 — 污点追踪（Taint Analysis）

对候选清单中的每一个点，执行以下追踪：

1. **向上追踪（Source）**：从命中行出发，沿调用链向上查找，直到找到数据的来源。判断来源是否属于以下类别：
   - `req.query` / `req.params` / `req.body` / `req.headers` → **用户可控（HTTP）**
   - 函数参数且调用方传入用户输入 → **用户可控（间接）**
   - 数据库查询结果被再次拼入 SQL → **二阶注入**
   - 环境变量 / 硬编码常量 → **不可控（通常安全）**

2. **向下追踪（Sink）**：确认数据最终进入 SQL 的方式：
   - 作为 `replacements` / `bind` 数组的元素 → 参数化（安全）
   - 作为 ORM `where: { col: value }` 的值 → ORM 处理（通常安全）
   - 进入模板字符串 / 字符串拼接 / `literal()` / `.raw()` 的字符串参数 → **危险 Sink**
   - 进入动态标识符（ORDER BY / 表名 / 列名）→ **危险 Sink（需白名单）**

3. **净化检查（Sanitizer）**：在 Source → Sink 路径上是否存在有效净化：
   - 白名单校验（枚举比对）→ 有效
   - parseInt / Number() 对纯数字场景 → 有效
   - 正则替换去除特殊字符 → 部分有效（需看正则质量）
   - escapeString / 引号转义 → 对标识符注入无效

---

## 阶段 3 — 风险分级

对每个经过阶段 2 确认的发现，使用 Skill 中的「严重性矩阵」评定等级：

| 等级 | 条件 |
|------|------|
| 🔴 高危 | 用户可控输入 → 无净化 → 进入 SQL 语法结构（WHERE/ORDER BY/子查询） |
| 🟡 中危 | 用户可控输入 → 有部分净化但不充分，或进入 LIKE/LIMIT/OFFSET |
| 🔵 低危 | 间接用户输入（如管理后台字段）→ 进入 SQL 结构 |
| ⚪ 信息 | 使用了 raw SQL 但当前路径无用户输入，属于「技术债」需持续关注 |

---

## 阶段 4 — 二阶注入专项

在阶段 1 命中点之外，额外搜索以下模式：
1. 数据写入操作（INSERT/UPDATE）中包含用户输入的字段。
2. 后续查询中，从同一张表读取该字段并拼入 SQL。
3. 批量操作、报表生成、导出功能中从 DB 读数据后构建 SQL。

标记所有「存储 → 读取 → 拼入」链路为 **二阶注入候选**。
